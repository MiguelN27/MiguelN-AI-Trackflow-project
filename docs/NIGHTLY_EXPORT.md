# Nightly Telemetry Export (DEV-53)

Every night, without anyone running it, `scripts/nightly_export.py`:

1. exports the previous UTC day of `telemetry_events` to `data/raw/telemetry_<YYYY-MM-DD>.csv`, unless that file already exists;
2. runs the business performance pipeline (`data/pipelines/pipeline.py`) as a subprocess;
3. records what happened, and when, in the `job_runs` table.

The OS crontab starts it through `scripts/cron/nightly_export.sh`. It is a process of its own: it shares nothing with the FastAPI server, and the API does not need to be running.

## Running it

```bash
python scripts/nightly_export.py                         # yesterday, in UTC
TARGET_DATE=2026-10-20 python scripts/nightly_export.py  # any day that has ended
npm run job:nightly-export                               # the same, through uv
```

It reads the repository's `.env` the way the API does, so `DATABASE_URL` and the other required settings must be there. `TARGET_DATE` must be `YYYY-MM-DD` and must name a day that has already ended in UTC. Otherwise the script logs an error and exits 2 without writing anything.

| Exit status | Meaning |
| --- | --- |
| 0 | Completed; or already completed for that date (duplicate); or another execution was running (aborted) |
| 1 | Failed. The `job_runs` row says why. |
| 2 | Configuration error: `TARGET_DATE` or the settings |
| 130 / 143 | Interrupted by Ctrl-C / SIGTERM. The row is marked `failed`. |

## What one run does

| Step | Detail |
| --- | --- |
| Target date | `TARGET_DATE`, or yesterday in UTC. The day is `[00:00 UTC, 00:00 UTC next day)`. |
| Export | The day's rows of `telemetry_events`, bounded on `timestamp` (as in `services/telemetry/analysis.py`), oldest first. The query runs in a `READ ONLY` transaction over `DATABASE_URL`, not PostgREST, whose 1000-row limit would silently truncate a busy day. Columns are the table's own: `id,timestamp,event_type,payload,tags,created_at`. Timestamps are ISO 8601 UTC; `payload` and `tags` are JSON with sorted keys. An empty day gives a header-only file. |
| Only if absent | If the day's file exists, the export is skipped. The rows are written to a hidden `.partial` file that is renamed into place only when complete, so a run killed mid-export never leaves a truncated file that a later run would accept. |
| Pipeline | `python -m data.pipelines.pipeline --week-start <Monday>`. The pipeline works in whole closed ISO weeks, so the Monday is the start of the last week that had closed by the end of the target date. For a Sunday, that is the week the Sunday ends; for any other day, the week before. Each night therefore recomputes the latest closed week, which absorbs late events, and Sunday's run (in the early hours of Monday) publishes the week that just ended. The pipeline's own upsert makes a recomputation that changes nothing a no-op. |
| Record | One `job_runs` row per execution: `pending` → `processing` → `completed` or `failed`, with `started_at`, `finished_at` and `error_message`. |

The CSV is a backup and audit snapshot. The pipeline reads the database, never this file. The exports carry pseudonymous user and session ids and are git-ignored (`data/raw/telemetry_*.csv`).

## `job_runs`

Created by `services/job_runner/service.py::ensure_schema` before every run (idempotent). The same table, as reviewable SQL, is in `services/job_runner/migrations/001_create_job_runs.sql`; `tests/test_job_runner_postgres.py` checks that both build the same table.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | generated by the job runner |
| `job_name` | `text` | `nightly_export` |
| `target_date` | `date` NOT NULL | the day the run is for |
| `status` | `text` | `pending`, `processing`, `completed` or `failed` (`job_runs_status_ck`) |
| `started_at` | `timestamptz` | set on `processing` |
| `finished_at` | `timestamptz` | set exactly when `completed` or `failed` (`job_runs_finished_ck`) |
| `error_message` | `text` | required on `failed` (`job_runs_error_message_ck`) |
| `created_at` | `timestamptz` | `now()` when the run claimed the job |

Indexes:
- `job_runs_job_name_target_date_idx` on `(job_name, target_date)` serves the idempotency check.
- `job_runs_one_active_idx`, unique on `(job_name)` where `status in ('pending', 'processing')`, is the lock.

RLS is on with no policies, as on every table the backend owns.

The table is in `public`, next to `telemetry_events`, and is deliberately separate from `reporting.pipeline_runs`, which belongs to the data layer. A pipeline run records what it computed: weeks, snapshot cutoff, row counts. A job run records the operational job that started it. A nightly run leaves one row in each.

## Idempotency and locking

`services/job_runner/service.py::run_job` decides, in this order:

1. **Abandoned runs.** An active row older than 6 hours is marked `failed` ("Abandoned: the run stopped without recording an outcome"). No real run takes that long: the pipeline is bounded at 3 hours. Only a process that was killed outright (SIGKILL, power loss) leaves such a row.
2. **Lock via `processing`.** If the job has a `pending` or `processing` row, the run logs the cancellation and exits 0 without writing anything. Two instances starting at the same moment can both pass that check. The unique index then refuses the second insert, and that instance aborts the same way. There is no lock table or lock column.
3. **Idempotency via `target_date`.** If a `completed` row exists for `(job_name='nightly_export', target_date)`, the run logs "skipped as a duplicate" and exits 0. Neither the export nor the pipeline runs again. The check uses the job name and the date; the job name alone would block every other day.
4. Otherwise it claims a `pending` row, marks it `processing`, does the work and marks it `completed`.

A failed day can simply be run again (`TARGET_DATE=<day>`). If its CSV was written before the failure, the file is kept and only the pipeline runs again. The day then has two rows, `failed` and `completed`.

## Failures

- **Any exception**, including Ctrl-C and SIGTERM, marks the row `failed` with `"<ExceptionClass>: <message>"` and is logged at ERROR with the traceback. Database errors keep only their class in the row, because a driver message can quote the server's host. The full message is in the log.
- **Pipeline exit status other than 0** fails the run. The stored message carries the status and the pipeline's last log line, for example `PipelineTriggerError: The data pipeline exited with status 1: RuntimeError: ...`. Exit 0 includes the pipeline skipping itself because another of its runs holds its slot. That is the pipeline's own rule, and the next night recomputes the same week anyway.
- **Timeout.** The pipeline gets 3 hours, its own longest possible run (4 attempts of 30 minutes plus 3 retry delays of 15). Its flow retries already ride out a database outage of about 45 minutes, so a run that fails during an outage takes that long to be marked failed.
- **Stopping the pipeline** (timeout, SIGTERM, Ctrl-C) happens in a fixed order:
  1. SIGTERM to the pipeline process alone. Prefect turns it into a crashed flow run and calls the crash hook, which marks the pipeline's own `reporting.pipeline_runs` row failed.
  2. After up to 30 seconds, SIGTERM to the rest of its process group. That stops Prefect's temporary API server, which the pipeline CLI runs as a separate process. Signalling the group first stops that server before the hook can use it, and the pipeline's row would stay `running` until its own 3-hour sweep.
  3. SIGKILL to anything that is left.
- **SIGKILL of the script itself** leaves the row `processing`, and nothing can prevent that. Runs within the next 6 hours abort on the lock, as they must, because they cannot tell a dead run from a live one. The first run after that marks the row failed and proceeds. The pipeline subprocess, in its own session, finishes on its own under its own concurrency guard.
- **The database is unreachable** before a row exists: the run logs the error and exits 1. Nothing could be recorded.

## Logs

One line per event on stderr, which the cron wrapper appends to `logs/nightly_export.log` (git-ignored):

```text
2026-10-25T23:29:32.446Z INFO job=nightly_export target_date=2026-10-24 status=pending Run 20c8705a-... recorded
2026-10-25T23:29:32.888Z INFO job=nightly_export target_date=2026-10-24 status=processing Started
2026-10-25T23:29:33.637Z INFO job=nightly_export target_date=2026-10-24 status=processing Exported 0 events to data/raw/telemetry_2026-10-24.csv
2026-10-25T23:29:33.638Z INFO job=nightly_export target_date=2026-10-24 status=processing Running the data pipeline for the week of 2026-10-12
2026-10-25T23:29:49.152Z INFO job=nightly_export target_date=2026-10-24 status=processing The data pipeline finished: status=completed weeks=2026-10-12 events_read=0 rows inserted/updated/unchanged/deleted=0/0/3/0
2026-10-25T23:29:49.583Z INFO job=nightly_export target_date=2026-10-24 status=completed Finished
2026-10-25T23:30:03.031Z INFO job=nightly_export target_date=2026-10-24 status=skipped Already completed for this date; skipped as a duplicate
```

- Every line carries a UTC timestamp, the level, the job name, the target date and the resulting status. Statuses: `pending`, `processing`, `completed`, `failed`, `skipped`, `aborted`.
- Starts, finishes and skips are INFO; failures are ERROR.
- The pipeline's own log is re-logged line by line as `status=processing pipeline | ...`. Each line keeps Prefect's level, and a Python traceback is logged as an error.
- The log grows by about 40 lines a night and is not rotated.

## Scheduling

```cron
30 3 * * * "/path/to/checkout/scripts/cron/nightly_export.sh"
```

Every day at **03:30 in the cron daemon's timezone** (UTC on servers). The script always derives the previous UTC day itself, so the time only has to fall after midnight UTC with room for late frontend batches. Those arrive within minutes: the emitter flushes every 10 seconds and retries with backoff.

03:30 meets that in every zone TrackFlow runs in:

| Zone | 03:30 local in UTC |
| --- | --- |
| UTC | 03:30 |
| Monterrey (UTC-6, no DST) | 09:30 |
| Zaragoza (UTC+1 / +2) | 02:30 / 01:30 |
| US Eastern, the development Mac (UTC-4 / -5) | 07:30 / 08:30 |

It also stays clear of the hours that daylight-saving changes skip or repeat.

**Install** (keeps any existing entries):

```bash
sed "s|REPO_DIR|$PWD|" scripts/cron/nightly_export.crontab > /tmp/nightly.cron
(crontab -l 2>/dev/null; cat /tmp/nightly.cron) | crontab -
crontab -l
```

Pass the file to `crontab` on stdin, as above. macOS `crontab <file>` truncates long paths.

**Uninstall:** `crontab -l | grep -v nightly_export.sh | crontab -`.

### Why the OS crontab

The ticket leaves the choice between crontab and a scheduler:

- **Not inside FastAPI** (APScheduler, `@repeat_every`, lifespan hooks). A job in the API process would run once per worker and stop when the API restarts. A failure in it would also share the server's main thread and memory.
- **Not the Prefect deployment.** The pipeline already has a Monday deployment, but serving it needs a long-lived Prefect server and runner. Nothing serves it permanently yet, and the nightly export is not a Prefect flow.
- **Crontab** is an independent OS process with nothing extra to keep alive. The same wrapper works on a Linux server and on the development Mac. The guarantees do not depend on the scheduler: the lock and the per-day idempotency live in the database. A double fire, a manual run during the scheduled one, or a second machine with the same crontab still gives one execution per day.

**For production**, the same wrapper can run in a dedicated scheduler container, for example a `scheduler` service in `docker-compose.yml` running supercronic with the crontab above. That container is not built yet: Docker is not installed on the machine this was developed on, so it could not be verified.

Known limitation: cron skips a run while the machine is off or asleep. This matters on a laptop, not on a server. A missed day is not caught up automatically; run it with `TARGET_DATE`.
